# 집 가 — 웹 배포와 알림 설계

> 스토어 출시를 접고 웹으로 전환한다. 그 결정이 바꾸는 것과, 함께 넣는 알림 체계.
>
> 작성일: 2026-08-26 · 상태: 확정 (구현 계획 대기)
>
> 선행 문서 — [설계 정리](zipGa.md) · [파장 흐름 설계](sessionEnd.md)

## 1. 배경

기존 설계는 **안드로이드 앱 단독 출시**를 전제했다. 그 전제를 웹으로 바꾼다.

### 1.1 웹으로 전환하는 이유

**설치가 사라진다.** 술자리에서 "앱 깔아"는 사실상 최대 장벽이다. 취한 사람에게 스토어를 열고 검색하고 설치하게 만드는 것과, 카톡으로 온 링크를 누르게 하는 것은 완전히 다른 일이다.

**iOS가 공짜로 들어온다.** 안드로이드 단독으로 정했던 건 iOS 빌드에 Mac·심사·개발자 계정이 필요했기 때문이다. 웹은 그 전부가 사라진다. 술자리 인원의 절반이 아이폰인데, 기존 설계로는 그 절반이 아예 참여할 수 없었다.

**배포가 정적 파일이다.** Supabase가 백엔드를 다 맡으므로 서버가 필요 없다. 빌드 결과물을 정적 호스팅에 올리면 끝이다.

### 1.2 대신 생기는 문제

브라우저 탭은 네이티브 앱보다 훨씬 공격적으로 얼어붙는다. **폰 화면이 꺼지면 탭이 멈추고 Realtime 연결이 끊긴다.**

이건 단순한 불편이 아니다. 방장이 세션을 시작했는데 내 폰이 주머니에 있으면 20초짜리 게임 3판이 그냥 지나가고, **평균 0점으로 강퇴된다.** 화장실 다녀오면 집에 가라는 소리를 듣는 것이다.

설계 정리 §5.3에서 "시간이 게임을 자동 시작하면 안 된다"고 막아둔 것과 같은 종류의 사고인데, **방장이 누른 뒤에는 그 구멍이 그대로 남아 있었다.** 알림은 그 구멍을 메운다.

## 3. §A 웹 배포

### A.1 초대 경로 — 링크와 QR이 같은 주소를 가리킨다

QR이 담는 값과 카톡으로 보내는 링크가 **완전히 같은 URL**이다. 관리 지점을 하나로 유지하기 위해서다.

```
https://<도메인>/room/ABC123
```

| 상황 | 방법 |
|---|---|
| 옆에 있다 | QR 스캔 |
| 멀리 있다 | 카톡으로 링크 |

방장 화면에는 QR과 그 아래 링크 텍스트, "링크 복사" 버튼을 함께 둔다. 스캔 결과가 URL이므로 두 경로가 같은 코드로 합류한다.

**경로 방식(`/room/ABC123`)을 쓴다.** 쿼리(`?room=`)보다 링크가 깔끔하고 QR도 짧아진다. 대신 호스팅에 SPA fallback 설정이 필요한데 Vercel·Cloudflare Pages 둘 다 한 줄이다.

`src/lib/deepLink.ts`가 두 형태를 모두 받는다.

```
https://<도메인>/room/{코드}   ← 웹 (신규)
jipga://room/{코드}            ← 기존
```

기존 스킴을 지우지 않는다. 패턴 하나 유지하는 비용이 거의 없고, 나중에 네이티브로 돌아갈 여지를 남긴다.

### A.2 URL 읽기 — 시작 시 한 번

앱이 뜰 때 `window.location`에서 방 코드를 한 번 뽑아 초기 화면을 정한다. 코드가 있으면 **닉네임 입력부터** 시작한다 — 기존 `S2` 흐름과 같다. 스캔이든 링크든 "코드를 손에 쥔 상태"로 들어오는 것은 동일하다.

**읽은 뒤 URL은 지우지 않는다.** 새로고침하면 같은 방으로 다시 들어가지므로 오히려 이득이다.

전 화면 라우팅(expo-router 등)은 도입하지 않는다. URL이 실제로 필요한 곳은 초대 링크 하나뿐이고, **게임 중 뒤로가기로 이탈하면 0점**이라 오히려 위험하다. 지금 팀 전원이 `App.tsx` 위에서 작업 중이라는 점도 고려했다.

### A.3 빌드와 호스팅 ✅ 완료

**배포됨 → https://zip-ga-frontend.vercel.app/**

설정은 `client/vercel.json`에 있다. 아래는 계획 당시의 기록이며, 실제 값은 그 파일이 기준이다.

```
빌드          npx expo export -p web           →  client/dist/
호스팅        Vercel (확정)
환경변수      EXPO_PUBLIC_SUPABASE_URL
              EXPO_PUBLIC_SUPABASE_PUBLISHABLE_KEY
SPA fallback  모든 경로 → /index.html
```

**HTTPS는 선택이 아니라 필수다.** QR 카메라 권한(`getUserMedia`)이 HTTPS에서만 열린다. 두 호스팅 모두 자동 제공한다.

`EXPO_PUBLIC_` 값은 번들에 인라인되어 누구나 볼 수 있다. 두 값은 원래 공개용(publishable)이며 실제 보호는 Postgres RLS가 한다. `service_role` 키는 절대 이 접두어로 넣지 않는다.

### A.4 PC 브라우저 — 막지 않는다

첫 화면에 "폰에서 여는 걸 권합니다" 한 줄만 둔다.

카카오T가 PC에서는 열리지 않지만, **벌칙 화면에 이미 "안 열렸나요? 설치하기" 폴백이 있어 사용자가 갇히지 않는다.** PC에서 방을 만들어 QR을 띄우고 나머지가 폰으로 스캔하는 흐름도 자연스럽게 성립한다.

## 4. §B iOS 지원

웹 전환으로 iOS가 지원 대상이 됐다. 실기기 검증을 다시 했다.

### B.1 실기기 검증 결과

안드로이드는 갤럭시 Chrome(2026-08-25), iOS는 iPhone(2026-08-26)에서 각각 확인했다.

| 방식 | 갤럭시 | iPhone |
|---|---|---|
| **`kakaot://`** | ✅ 열림 | ✅ **열림** |
| `intent://…package=com.kakao.taxi…` | ❌ 스토어로 감 | ❌ 안드로이드 전용 문법 |
| `kakaotaxi://` · `daumtaxi://` | ❌ | ❌ |
| 플레이스토어 링크 | ✅ 스토어 앱 | ⚠️ **웹페이지만 뜸** |

**`kakaot://`가 양쪽 다 동작한다.** 벌칙 딥링크는 플랫폼 분기 없이 하나로 간다.

### B.2 스토어 폴백은 갈라야 한다

iOS에서 플레이스토어 링크는 "열리기는" 하지만 **안드로이드 앱 페이지가 웹으로 뜰 뿐 설치가 되지 않는다.** 아이폰 미설치 사용자가 막다른 길로 간다.

`src/lib/kakaoTaxi.ts`의 폴백을 플랫폼별로 나눈다.

```
안드로이드  https://play.google.com/store/apps/details?id=com.kakao.taxi
iOS         https://apps.apple.com/kr/app/id981110422
```

웹에서는 `navigator.userAgent`로 iOS 여부를 판별한다. 판별에 실패하면 플레이스토어를 기본으로 둔다 — 안드로이드 사용자가 다수이고, 잘못 가더라도 §A.4의 수동 탈출구가 받아준다.

### B.3 웹에서는 `Linking`을 쓸 수 없다

**현재 코드에 이 문제가 있다.** 웹에서 벌칙 딥링크가 아무 반응 없이 실패하고, 안내조차 뜨지 않는다.

`react-native-web`의 `Linking.openURL` 구현이 원인이다.

```js
openURL(url, target = '_blank') {
  try {
    window.open(url, '_blank', 'noopener')
    return Promise.resolve()          // ← 항상 성공으로 처리된다
  } catch (e) {
    return Promise.reject(e)
  }
}
```

**`window.open`은 실패해도 예외를 던지지 않는다.** `null`을 반환할 뿐이다. 스킴이 열리지 않아도 `Promise.resolve()`가 나오고, 우리 코드는 `'opened'`를 반환한다. 그러면 `GoingHome`이 "열렸구나" 판단해 **수동 탈출구까지 숨긴다.** 아무 일도 안 일어나는데 안내도 없는 상태가 된다.

문제가 둘 더 있다.

- **커스텀 스킴은 `location.href`로 열어야 한다.** 새 탭(`window.open`)으로 열면 팝업 차단에 걸리거나 빈 탭만 뜬다. RNW는 `tel:`만 특별 처리하고 나머지를 전부 `window.open`으로 보낸다.
- **웹에는 "앱이 안 열렸다"는 신호가 없다.** 브라우저가 알려주지 않는다. 예외를 잡아 판단하는 구조 자체가 웹에서 성립하지 않는다.

#### 웹에서는 판정하지 않는다

브라우저에는 "앱이 열렸는지"를 알려주는 신호가 없다. `visibilitychange`와 타이머로 흉내 낼 수는 있지만 **추론이라 틀린다.** 틀렸을 때의 대가가 크다 — 정상적으로 카카오T를 연 사람이 돌아왔을 때 스토어로 보내지거나, 앱이 통째로 사라진다.

**추측하는 대신 모른다고 인정하고, 화면이 항상 안내를 보여준다.**

```
window.location.href = 'kakaot://'
// 끝. 판정도 타이머도 없다.
```

웹의 반환값은 `'unknown'` 하나다.

#### 화면이 판정을 대신한다

`S10` 귀가 화면에 설치 안내를 상시 노출한다.

```
        집 가
   조심히 가세요

  ┌─────────────────────────┐
  │  카카오T가 없으신가요?    │
  │  앱이 안 열렸다면          │
  │  여기서 설치하세요         │
  │    [ 설치하러 가기 ]       │
  └─────────────────────────┘

      [ 아직 안 갈래 ]
```

**앱이 열린 사람은 이 화면을 볼 일이 없다.** 이미 카카오T로 넘어가 택시를 잡고 있다. 못 연 사람만 이 화면 앞에 남고, 그 사람에게는 설치 버튼이 정확히 필요한 것이다.

사용자가 직접 누르는 순간이라 팝업 차단에도 걸리지 않는다.

#### 플랫폼 분기

| | 여는 방법 | 실패 감지 | 스토어 |
|---|---|---|---|
| 네이티브 | `Linking.openURL` | **예외 — 진짜 신호** | 자동 폴백 |
| 웹 | `location.href` | **하지 않음** | 화면 안내 |

네이티브에서는 예외가 추측이 아니라 실제 신호이므로 자동 폴백이 동작한다. 열린 것이 확실할 때(`'opened'`)만 안내를 접는다.

## 5. §C 알림 1단계 — 인앱

서버 코드가 필요 없는 범위. **폰을 보고 있거나 손에 쥐고 있으면 확실히 알게 된다.**

### C.1 복귀 동기화 — 가장 중요하다

탭이 얼어 있던 동안 온 Realtime 신호는 이미 지나갔다. 현재 `getActiveSessionId`는 `roomId`가 바뀔 때만 돌아서 그것을 메울 트리거가 없다.

```
document.visibilitychange (visible)  →  getActiveSessionId(roomId) 재조회
```

이게 없으면 이런 일이 난다.

> 폰을 주머니에 넣음 → 방장이 게임 시작 → 꺼내보니 아직 로비 → 이미 판이 지나감

**푸시를 넣더라도 이 처리는 반드시 있어야 한다.** 푸시를 못 받는 경로(권한 거부, iOS 미설치)가 항상 존재하기 때문이다.

### C.2 소리와 진동

세션이 시작될 때(`lineup` 진입) 울린다.

| 수단 | 지원 |
|---|---|
| Web Audio 짧은 알림음 | 전 플랫폼 |
| `navigator.vibrate` | 안드로이드만 (iOS 미지원) |

브라우저는 사용자 제스처 없이 소리를 재생하지 못한다. **방에 입장하는 순간(사용자가 버튼을 누른 시점)에 오디오 컨텍스트를 미리 열어둔다.**

### C.3 화면 유지 — 로비에서만

```
navigator.wakeLock.request('screen')
```

로비에서 대기하는 동안 화면이 꺼지지 않게 한다. 화면이 살아 있으면 탭이 얼지 않아 신호를 즉시 받는다. iOS는 16.4+에서 지원한다.

**로비에서만 건다.** 술자리 3~4시간 내내 화면을 켜두면 배터리가 죽는다. 세션 중에는 어차피 화면을 보고 있으므로 필요 없다.

기본값은 꺼둔다 — 배터리를 소모하는 동작을 사용자 모르게 켜지 않는다.

### C.4 설정

`Settings` 화면에 이미 효과음·배경음 토글이 있다. 같은 자리에 둘을 더한다.

- 세션 시작 알림 (기본 켬)
- 로비에서 화면 켜두기 (기본 끔)

## 6. §D 알림 2단계 — Web Push

화면이 꺼져 있어도 도착한다.

### D.1 안드로이드는 설치가 필요 없다

푸시를 받으려면 Service Worker가 필요하다. 하지만 **홈 화면 추가까지 필요한 것은 iOS뿐이다.**

| | Service Worker | 홈 화면 추가 |
|---|---|---|
| 안드로이드 Chrome | 필요 | **불필요** |
| iOS Safari·Chrome | 필요 | **필수** (iOS 16.4+, Apple 정책) |

**안드로이드 사용자는 알림 권한만 허용하면 끝이다.** 설치를 하지 않는다. iOS에만 한 단계가 더 붙는다.

```
링크로 들어옴  →  즉시 사용 가능 (설치 없음)
                      │
                      ├─ 안드로이드 → 알림 권한 허용하면 끝
                      └─ iOS       → 권한 + "홈 화면에 추가" 안내 (선택)
```

**iOS에서 추가하지 않아도 앱은 완전히 동작한다.** 푸시만 오지 않고 §C의 인앱 알림은 그대로 온다.

이렇게 두면 **"설치가 없다"는 웹 전환의 최대 장점을 깎지 않으면서** 원하는 사람에게만 알림을 준다. 안내는 로비에 한 번, 작게 띄운다. 거절하면 다시 묻지 않는다.

### D.2 구조

```
방장이 세션 시작
      │
      ├─ start_session RPC (기존)
      │
      └─ Edge Function notify_session_start(session_id) 호출
                │
                ├─ 호출자가 그 방의 방장인지 검증 (JWT의 auth.uid())
                ├─ 방의 다른 참가자 구독 조회
                └─ Web Push 전송 (VAPID 서명)
```

**방장 클라이언트가 Edge Function을 부른다.** PL/pgSQL에서 HTTP를 쏘려면 `pg_net` 확장이 필요한데, 그것까지 끌어들일 이유가 없다.

### D.3 스키마

```sql
create table push_subscriptions (
  player_id   uuid primary key references players(id) on delete cascade,
  endpoint    text not null,
  p256dh      text not null,
  auth        text not null,
  created_at  timestamptz not null default now()
);

alter table push_subscriptions enable row level security;

-- 본인 구독만 등록·삭제할 수 있다. 조회는 Edge Function이 service_role로 한다.
```

`player_id`가 PK이므로 한 사람당 구독 하나다. 기기를 바꾸면 덮어쓴다.

### D.4 Edge Function

```
supabase/functions/notify-session-start/index.ts   (Deno)
```

시크릿 — `VAPID_PUBLIC_KEY` · `VAPID_PRIVATE_KEY` · `SUPABASE_SERVICE_ROLE_KEY`

공개키는 클라이언트에도 필요하므로 `EXPO_PUBLIC_VAPID_PUBLIC_KEY`로 함께 노출한다. **비밀키는 Edge Function 시크릿에만 둔다.**

### D.5 "Edge Function 0개"가 깨진다

백엔드 명세 §0은 **"Edge Function 0개로 출시 가능하다"**고 적고 있다. 이 결정으로 그 전제가 깨진다.

받아들이는 이유는 하나다 — **푸시를 보내려면 VAPID 비밀키로 서명해야 하고, 그 키는 클라이언트에 둘 수 없다.** 서버 없이 우회할 방법이 없다.

대신 **함수는 이 하나로 끝낸다.** 다른 로직을 여기로 옮기지 않는다. 나머지는 그대로 RPC로 간다.

### D.6 무엇을 푸시하지 않는가

**세션 주기 도달 알림은 넣지 않는다.**

30분이 지났음을 서버가 알리려면 서버 타이머가 필요한데, 이 설계에는 타이머가 없다(백엔드 명세 §6). `pg_cron`을 도입하면 가능하지만 **관리 대상이 늘어나는 것에 비해 얻는 게 적다.**

주기 알림이 정말 필요한 사람은 방장 한 명뿐이고, 방장은 시작을 누르려고 폰을 보고 있을 가능성이 높다. §C의 인앱 배지로 충분하다.

**푸시하는 것은 "세션이 시작됐다" 하나다.** 0점 강퇴를 막는다는 목적에 정확히 대응한다.

## 8. §F 남는 위험

**새로고침하면 진행 중인 세션 상태가 날아간다.** 전 화면 라우팅을 넣지 않은 대가다. 방 코드는 URL에 남으므로 다시 들어갈 수 있지만, 게임 중이었다면 그 판은 놓친다. 실사용에서 새로고침할 일이 드물다고 보고 감수한다.

**웹의 딥링크 성공 판정은 추론이다.** 앱 전환이 느리면 스토어로 잘못 보내고, 사용자가 그 순간 다른 앱으로 전환하면 "열렸다"로 본다. 웹에서 수동 탈출구를 항상 노출하는 이유다 (§B.3).

**iOS 사용자가 홈 화면에 추가하지 않으면 푸시를 못 받는다.** §C의 인앱 알림과 복귀 동기화가 그 경우의 방어선이다. 푸시를 유일한 방어선으로 두지 않는 이유다.

**iOS Safari 카메라 권한 UX가 까다롭다.** HTTPS면 열리는 것이 정상이지만, 코드 직접 입력 폴백이 이미 있어 최악은 막힌다.

**소리 자동재생 정책.** 브라우저는 사용자 제스처 없이 소리를 못 낸다. 입장 시점에 오디오 컨텍스트를 열어두는 것으로 대응하지만, 그 시점이 너무 이르면 브라우저가 컨텍스트를 정지시킬 수 있다. 실기기 확인이 필요하다.
